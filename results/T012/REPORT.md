## 4. 与预期不符之处

### 4.1 仓库更新只能由用户在自有窗口完成

我的工具窗口无法覆盖已存在的文件：`git merge --ff-only` 连续两次 90 秒、240 秒无响应，`git checkout-index -f` 对 13 个文件逐个 30 秒超时，全部失败。新建文件正常，覆盖旧文件被拒。最后请用户在自己的窗口执行 `git pull --ff-only`，一次成功（`f6bf1fc..d1904dd`，13 个文件、876 行新增）。

第一次用户执行时又被残留的 `.git/ORIG_HEAD.lock` 挡住（我前面 merge 挂死留下的），清掉后成功。

### 4.2 全量 pytest 再次挂住，只跑了新增测试

`python -m pytest -q` 跑到 **30 分钟仍无输出**，进程 CPU 近乎 0，日志 0 字节，人工终止（与 T010 报告 4.7 节同一现象）。

随后只跑新增的测试文件：

```
6 passed in 52.62s
```

**全量测试在本机没有拿到通过结果**。代码本身没有被修改，`verify_integrity` 75 个受保护文件全部通过。

### 4.3 `repurchase_60` 没有 IC

`factor_table_v12.csv` 里这一行 `ic`、`icir`、`t_nw`、`spread_*`、`monotonicity`、`turnover` 全为空，只有 `prior_sign = 1` 和 `family = 公司事件`。它的覆盖率是 **0.1209**。同样的空值没有出现在另外 23 个新因子上。

### 4.4 三个因子的覆盖率低于 15%

`unlock_30` **0.0216**、`repurchase_60` **0.1209**、`an_rev_eps` 0.2978。前两个的样本量只有全样本的 2% 和 12%，它们的 IC 与 t 值是在这一小部分样本上算出来的，与其他因子不可直接比较。

### 4.5 实际耗时远低于任务单估计

任务单写 1.5–3 小时，实际 **1 小时 17 分**。`models` 阶段 3,892 秒占 84%，四个模型的耗时差异很大（438 秒到 1,575 秒），回归目标比排序目标快 2.5–3 倍。

## 6. 问题与建议

### 6.1 `repurchase_60` 的空结果建议在脚本里显式标注

现在这一行只有表头能看出缺值。建议在因子表里加一列 `status`（`ok`/`insufficient_sample`），否则下游读到空 IC 会当作 0 处理。

### 6.2 建议给因子表加一列"样本量"

`unlock_30` 与 `an_rev_eps` 的覆盖率差 14 倍，IC 的可比性完全取决于样本量。现在 `factor_table_v12.csv` 没有 `n` 列，只能靠 `factors_v2_summary.json` 的覆盖率间接推断。

### 6.3 全量 pytest 在本机不可用，需要设计方决定怎么处理

T010、T012 两次都在 15–30 分钟处挂死，T011 那次却完整通过（83 passed）。这不是代码问题（`verify_integrity` 与新增测试都通过），但"提交前必须贴 pytest 原文"这一条在本机无法稳定满足。建议设计方明确：挂住时是否允许只贴新增测试的结果并注明。
